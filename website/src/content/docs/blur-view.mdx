`BlurView` is the standard, cross-platform blur component. iOS uses UIKit's `UIVisualEffectView`. Android 12 and later blur on the GPU, and Android 11 and earlier use [QmBlurView](https://github.com/QmDeve/QmBlurView). Web uses CSS `backdrop-filter`.

## Basic usage

```tsx
import { BlurView } from '@sbaiahmed1/react-native-blur';

<BlurView
  blurType="light"
  blurAmount={20}
  style={{
    position: 'absolute',
    top: 100,
    left: 50,
    right: 50,
    height: 200,
    borderRadius: 20,
  }}
>
  <Text>Content with blur background</Text>
</BlurView>
```

## Advanced usage

```tsx
<BlurView
  blurType="systemMaterial"
  blurAmount={50}
  reducedTransparencyFallbackColor="#FFFFFF80"
  style={{ padding: 20, borderRadius: 15 }}
>
  <Text>Advanced blur with a custom accessibility fallback</Text>
</BlurView>
```

## Web behavior

On react-native-web, `BlurView` draws each `blurType` with the blur, saturation and tint of the same type on iOS, as a CSS `backdrop-filter` layer under a tint. Children render above the blur, sharp, the same layering as native.

`blurAmount` sets how much of that material draws, as on iOS. At 100 it draws the whole material, at 50 half the blur, half the tint and half the extra saturation, and at 0 nothing.

`regular`, `prominent` and the `system*Material` types without a `Light` or `Dark` suffix follow Dark Mode in the browser, as they follow it in the app on iOS. A few iOS materials change with the content behind them, `systemChromeMaterial` most of all. Web draws the closest fixed match for those.

- `overlayColor` paints above the blur, below children, like on native.
- During server-side rendering, the types that follow Dark Mode draw their light material. They switch to dark after hydration when the browser prefers it.
- In browsers without `backdrop-filter`, and during server-side rendering, only the tint remains. `expo-blur` degrades the same way.
- During hydration, the initial client render uses the same tint-only markup as the server. Supported browsers then turn the blur on. Client-only rendering turns it on right away.
- `blurRounds`, `reducedTransparencyFallbackColor`, and `ignoreSafeArea` are native-only no-ops.
- A forwarded `ref` resolves to the root `View` (a DOM element) instead of a native view.

## Android behavior

On Android 12 and later, a blur view blurs the views drawn behind it on the GPU. On Android 11 and earlier, QmBlurView captures the view tree around the blur into a downsampled bitmap and blurs it on the CPU. The capture covers the nearest `react-native-screens` Screen, or the React root when there is none. In practice:

- **Content drawn on top of a blur view stays out of it on Android 12 and later**, as on iOS. On Android 11 and earlier the capture includes anything rendered above the blur inside the capture root, which shows up as a blurred halo under the crisp original. If the halo shows in a design, move that content outside the capture root (e.g. a portal above the navigator).
- **Blur and glass views show each other on Android 12 and later.** Where two of them overlap, the top one shows the one below it, with its text and tint.
- **`blurRounds` only changes Android 11 and earlier.** Each pass adds a CPU blur pass, and lowering it trades quality for less work. Measure on target devices.
- **In-app screenshots show the tint without the blur on Android 12 and later.** A screenshot that draws your views into a bitmap gets the blur view's tint only. System screenshots show the blur.
- **The blur falls back to a screen capture if the library cannot read the views behind it.** The library then logs a warning tagged `RNBackdrop`. Content drawn on top shows as a halo, and overlapping blur and glass views leave each other out.
